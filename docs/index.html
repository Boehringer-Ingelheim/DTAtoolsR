PART 1

🚀 Check Your Data in 5 Minutes

📦 What is DTAtools?

DTAtools is an R package that validates tabular data files (CSV or TSV) against a Data Transfer Agreement specification written in YAML — before you send the data to a partner, a regulator, or a data warehouse. Think of it as a spell-checker for your clinical or study data: it reads your spec, reads your data, and tells you exactly what's wrong and where.

📄 YAML Spec
→
⚙️ DTAtools
←
📊 Your Data
→
✅ PASS
/
❌ ERRORS
🎯
Catch errors early Find problems before submission, not after rejection.
🔄
Auto-read column types Numbers, dates, and text are parsed according to your spec.
📋
Detailed error reports Exact row numbers, column names, and reasons for every failure.

📥 Installation

Install DTAtools from GitHub using remotes:

R
remotes::install_github("Boehringer-Ingelheim/DTAtoolsR")
library(DTAtools)
💡
Reproducibility tip

For production workflows, use renv to lock the exact package version: renv::snapshot() after installing, then renv::restore() on any other machine.

🗺️ The 5-Step Workflow

Every DTAtools session follows the same five steps. Learn these once and you'll never forget them.

1
Load your specification — read a YAML file that describes what your data should look like
↓
2
Load your data file — attach a CSV or TSV file to the dataset defined in your spec
↓
3
Run validation — call check() to perform all import, column spec, and rule checks
↓
4
See results — call results() for a summary table showing PASS / FAIL per dataset
↓
5
Drill into errors — use messages() for the error list and inspect() for row-level detail

🧪 Your First Validation

Here is the complete beginner workflow from start to finish:

R
library(DTAtools)

# Step 1: Load the specification (YAML defines what your data should look like)
dta <- read_dta_from_yaml("path/to/clinical_dta.yaml")

# Step 2: Load your data file
dta <- load_file(dta, dataset = "clinical_data", file = "path/to/your_data.csv")

# Step 3: Validate everything
dta <- check(dta)

# Step 4: See results — did your data pass?
results(dta)

# Step 5: If there are errors, see what they are
messages(dta)
💡
Always assign the result back!

dta <- check(dta) — check() returns the updated object with validation results attached. If you forget the assignment, your results will be lost.

📊 Understanding the Output — What results() Shows

results() returns a data frame with one row per validated dataset. Here is what each column means:

Column Description Possible values
dataset / target Which dataset and table was validated (dataset is the dataset name, target is the table name within it) Name strings
status Overall validation result as a string "validated" / "failed" / "skipped" / "not_validated"
ok Boolean pass/fail — use this for programmatic checks (e.g. if (results(dta)$ok)) TRUE / FALSE
n_columnspec_errors Column rule violations — wrong type, invalid value, pattern mismatch, etc. Integer ≥ 0
n_rule_errors Cross-column logic violations (see Part 3) Integer ≥ 0
n_import_errors Values that couldn't be read in the declared type Integer ≥ 0, or NA if result predates import checking
⚠️
Even one import error fails the table

A dataset with n_import_errors = 1 will always have ok = FALSE (status: "failed"), even if all column spec and rule checks would otherwise pass.

🔍 Finding Your Errors

Use a three-level drill-down to zero in on exactly what went wrong:

results(dta) →  "2 tables failed"
↓
messages(dta) →  "AGE column: 3 errors on rows 5, 7, 12"
↓
inspect(dta, id = msgs$id[1]) →  "Row 5: AGE='unknown' — cannot be read as a number"

The messages() output has rows colored by error type:

SourceColorExample message
import 🔴 red Value "unknown" cannot be read as SAS Num
columnspec 🟠 orange Value "V99" not in allowed values list
rule 🟡 yellow CONSENT='YES' but CONSENT_DATE is empty (rule: consent_requires_date)
PART 2

📄 Understanding Specifications

🗂️ What is a YAML Specification?

A YAML spec file is a plain-text description of your data: which columns exist, what type they hold, whether they can be empty, what values are allowed, and what cross-column rules must hold. DTAtools reads this file and uses it as the ground truth to validate your data against.

YAML
datasets:
  - name: my_data
    type: tabular
    files:
      filename: "my_data.csv"
      type: csv
    columns:
      - id: PATIENT_ID
        type: SAS Char
        nullable: false
        pattern: "^PAT[0-9]{4}$"   # must look like PAT0001

      - id: AGE
        type: SAS Num
        nullable: false             # every patient must have an age

      - id: VISIT
        type: SAS Char
        nullable: false
        values:                     # closed list of allowed values
          - V01
          - V02
          - V03

      - id: STATUS
        type: SAS Char
        nullable: true              # allowed to be empty
        values:
          - COMPLETED
          - DROPPED
💡
The name must match exactly

The name: field in your YAML must be passed as-is to load_file(..., dataset = "my_data"). They are case-sensitive.

⚠️
Two YAML shapes: full DTA vs. single dataset

The YAML above (starting with datasets:) is the format for read_dta_from_yaml(), which loads a full agreement with metadata.

If you use read_dataset_from_yaml() (for a single dataset without metadata), the YAML must start directly with name:, type:, files:, columns: — no datasets: wrapper. See Section 4.1 for an example.

🏷️ Column Types — What does "SAS Char" mean?

DTAtools uses SAS-style type names. This controls how values are read from the raw text of your CSV file, not just how they are validated.

TypeStored asExample values
SAS CharText (character)"SUBJ001", "V03"
SAS NumNumber (double)32, 72.5
SAS IntInteger42
SAS DateText (validated by pattern)"2024-06-19"
SAS TimeText (validated by pattern)"14:30:00"
SAS DateTimeText (validated by pattern)"2024-06-19T14:30:00"
⚠️
Type matters for reading!

A column declared SAS Num will turn '007' into 7 (the leading zeros are lost). A column declared SAS Char will keep '007' as '007'. This is intentional — choose your types carefully!

🔧 Column Properties Reference

All properties you can set on a column in the YAML spec:

PropertyRequired?DescriptionExample
id ✔ yes Column name — must match the CSV header exactly PATIENT_ID
label optional Human-readable label for documentation Patient Identifier
type optional SAS type (see above) SAS Char
nullable optional Whether empty / NA values are allowed true or false
values optional Closed list of allowed values. Mutually exclusive with pattern. [V01, V02, V03]
pattern optional Regex that every value must match. Mutually exclusive with values. ^PAT[0-9]{4}$
length optional Maximum character length 12
format optional SAS format string (documentation only) SAS $10.
description optional Free-text documentation Planned visit code
❌
values and pattern are mutually exclusive

You cannot specify both on the same column. Use values for a finite list, or pattern for a regular expression constraint.

🚦 Three Types of Errors Explained

DTAtools distinguishes three fundamentally different kinds of problems in your data:

🔴 Import Errors — "The value can't even be read"

The column is declared SAS Num but the cell contains "unknown". R can't convert that to a number, so it becomes NA and an import error is recorded.

  • Always causes ok = FALSE (status: "failed")
  • Cell is stored as NA
  • See import_raw in inspect()
🟠 Column Spec Errors — "Readable, but breaks a column rule"

The value was successfully parsed, but it violates a constraint on the column itself.

  • Value not in values list
  • Value fails pattern regex
  • Required column is empty (nullable: false)
  • String exceeds length
🟡 Rule Errors — "Values OK individually, but break a cross-column rule"

Each value is valid on its own, but the combination violates a rule.

  • CONSENT='YES' but CONSENT_DATE is empty
  • AGE=70 but max allowed is 65
  • SUBJECT_ID+VISIT is not unique
PART 3

⚖️ Validation Rules

📖 Rules Overview

Rules check that columns make sense together, not just individually. They are defined under a rules: key inside your dataset spec and run after all column spec checks have passed.

DTAtools supports four built-in rule types:

  • col_condition — if/then logic between columns
  • col_range — numeric min/max constraint on a single column
  • col_unique — uniqueness constraint (single column or combination)
  • group_condition — group-Level If/Then Logic

🔀 col_condition — If/Then Logic

This is the most powerful rule type. It lets you say:

IF [condition on column A]
→
THEN [constraint on column B]
YAML
# IF consent was given, the consent date must be filled
- id: consent_requires_date
  type: col_condition
  condition:
    CONSENT:
      equals: "YES"
  then:
    CONSENT_DATE:
      empty: false

# IF visit is V03, status must be COMPLETED
- id: v03_must_be_completed
  type: col_condition
  condition:
    VISIT:
      equals: V03
  then:
    STATUS:
      equals: COMPLETED

All supported operators for both condition and then:

Operator In condition? In then? Example
equals✅✅equals: "YES"
not_equals✅✅not_equals: DROPPED
empty✅✅empty: false
in✅✅in: [V01, V02, EOT]
not_in✅✅not_in: [REJECTED]
pattern✅✅pattern: "^PAT[0-9]{4}$"
greater✅✅greater: 0
greater_equal✅✅greater_equal: 18
less✅✅less: 200
less_equal✅✅less_equal: 65
min + max✅✅min: 10 + max: 100

📏 col_range — Numeric Range Check

Validates that all values in a numeric column fall within a specified range.

YAML
- id: age_range
  type: col_range
  column: AGE
  min: 18
  max: 65
💡

Both min and max are inclusive. A patient aged exactly 18 or exactly 65 will pass this rule.

🔑 col_unique — Uniqueness Constraint

Ensures no duplicate values exist — either in a single column or across a combination of columns.

YAML
# Single column must be unique
- id: patient_unique
  type: col_unique
  column: PATIENT_ID

# Combination of PATIENT_ID + VISIT must be unique
# (same patient can appear in multiple visits, just not twice in the same visit)
- id: patient_visit_unique
  type: col_unique
  column:
    - PATIENT_ID
    - VISIT

🧩 group_condition — Group-Level If/Then Logic

Unlike col_condition, which evaluates each row independently, group_condition first groups rows by one or more columns and then applies constraint logic across the whole group. This lets you express rules like "if any row in this subject's group has consent, then all rows in the group must have a consent date."

💡
When to use group_condition instead of col_condition

col_condition checks each row against the rule on its own — it doesn't know about the other rows for that subject. Use group_condition when the rule depends on what happened across multiple rows belonging to the same entity (subject, sample, visit, …).

Structure

A group_condition rule has three parts:

  1. group_by — which columns define a group (e.g. SUBJECT_ID)
  2. conditions — named Boolean flags, each a column test (same operators as col_condition)
  3. constraints — rules over those flags: requires or mutually_exclusive

Constraint types

TypeAliasesMeaning
requires implies IF condition if holds (scope: any/all rows in group), THEN condition then must hold (scope: any/all)
mutually_exclusive not_both left and right conditions cannot both be true in the same group
Scope valueMeaning
any (default)At least one row in the group satisfies the condition
allEvery row in the group satisfies the condition

YAML examples

YAML — requires constraint
# IF any row in the subject group has CONSENT="YES",
# THEN all rows in the group must have a CONSENT_DATE
- id: consent_requires_date_per_subject
  type: group_condition
  group_by:
    - SUBJECT_ID
  conditions:
    c_consent_yes:
      CONSENT:
        equals: "YES"
    c_consent_date_present:
      CONSENT_DATE:
        empty: false
  constraints:
    - id: consent_needs_date
      type: requires        # alias: implies
      if: c_consent_yes
      then: c_consent_date_present
      if_scope: any         # true if ANY row in group matches
      then_scope: all       # requires ALL rows in group to match
YAML — mutually_exclusive constraint
# A sample can't be both "failed QC" and "reported with a result" in the same group
- id: failed_vs_reported
  type: group_condition
  group_by:
    - SUBJIDN
    - VISIT
  conditions:
    c_failed:
      GFREASND:
        empty: false     # a failure reason is populated
    c_reported:
      GFORRES:
        empty: false     # a numeric result is present
  constraints:
    - id: qc_fail_and_result_are_exclusive
      type: mutually_exclusive   # alias: not_both
      left: c_failed
      right: c_reported

R — constructing in code

R
group_rule <- DTARuleGroupCondition(
  id       = "consent_requires_date_per_subject",
  group_by = "SUBJECT_ID",
  conditions = list(
    c_consent_yes = list(CONSENT = list(equals = "YES")),
    c_consent_date_present = list(CONSENT_DATE = list(empty = FALSE))
  ),
  constraints = list(
    list(
      id         = "consent_needs_date",
      type       = "requires",      # or "implies"
      `if`       = "c_consent_yes",
      `then`     = "c_consent_date_present",
      if_scope   = "any",           # "any" or "all"
      then_scope = "all"
    )
  )
)

# Attach to a spec collection alongside other rules
specs_with_group_rule <- DTAColumnSpecCollection(
  columns = list(
    SUBJECT_ID   = DTAColumnSpec(id = "SUBJECT_ID",   type = "SAS Char", nullable = FALSE),
    CONSENT      = DTAColumnSpec(id = "CONSENT",      type = "SAS Char", nullable = TRUE,
                                 values = list("YES", "NO")),
    CONSENT_DATE = DTAColumnSpec(id = "CONSENT_DATE", type = "SAS Char", nullable = TRUE)
  ),
  rules = list(group_rule)
)

🔬 Advanced Usage

📂 Validating a Single Dataset (without full DTA metadata)

If you just have a single dataset spec (not a full DTA with metadata), use read_dataset_from_yaml() instead of read_dta_from_yaml():

R
# Load just one dataset definition (no top-level metadata)
# Note: the YAML must start directly with name/type/files/columns
#   (no surrounding "datasets:" wrapper — that's only for read_dta_from_yaml())
ds <- read_dataset_from_yaml("my_dataset_spec.yaml")

# handler_index = 1 selects the first file handler defined in the YAML's files: block
ds <- load_file(ds, file = "my_data.csv", handler_index = 1)
ds <- check(ds)
results(ds)

🏗️ Building Specs Programmatically in R

You don't have to write YAML manually — you can build specifications entirely in R code:

R
library(DTAtools)

# Define columns
col_id    <- DTAColumnSpec(id = "PATIENT_ID", type = "SAS Char", nullable = FALSE,
                           pattern = "^PAT[0-9]{4}$")
col_age   <- DTAColumnSpec(id = "AGE",        type = "SAS Num",  nullable = FALSE)
col_visit <- DTAColumnSpec(id = "VISIT",      type = "SAS Char", nullable = FALSE,
                           values = list("V01", "V02", "V03"))

# Group into a collection
my_specs <- DTAColumnSpecCollection(
  columns = list(PATIENT_ID = col_id, AGE = col_age, VISIT = col_visit)
)

# Create a dataset with inline data
my_data <- data.frame(
  PATIENT_ID = c("PAT0001", "PAT0002"),
  AGE        = c(32, 45),
  VISIT      = c("V01", "V02")
)

ds <- DTADataSetTabular(name = "my_dataset", specs = my_specs,
                        tables = list(my_table = my_data))
ds <- check(ds)
results(ds)

📐 Building Rules Programmatically

R
# Range rule
age_rule <- DTARuleColRange(id = "age_range", columns = "AGE", min = 18, max = 65)

# Uniqueness rule
unique_rule <- DTARuleColUnique(id = "patient_visit_unique",
                                columns = c("PATIENT_ID", "VISIT"))

# Condition rule: IF CONSENT == "YES" THEN CONSENT_DATE must not be empty
condition_rule <- DTARuleColCondition(
  id        = "consent_requires_date",
  condition = list(CONSENT      = list(equals = "YES")),
  then      = list(CONSENT_DATE = list(empty  = FALSE))
)

# Attach rules to specs
specs_with_rules <- DTAColumnSpecCollection(
  columns = list(...),
  rules   = list(age_rule, unique_rule, condition_rule)
)

⚠️ Import Errors in Detail

Import errors are fundamentally different from column spec and rule errors. They happen before validation — during the read phase.

❌
Key distinction

A SAS Num column with cell "unknown" → import error (NA stored) AND possibly a column spec error if nullable: false.

Use msgs <- messages(ds); msgs[msgs$source == "import", ] to filter to just import errors.

Use inspect(ds, id = N) to see import_raw (original text), import_declared_type, and import_reason.

The import_reason column has two possible values:

ReasonMeaningExample
not_convertible Value has no numeric/date prefix at all "unknown", "n/a"
trailing_residue Value has a valid prefix but trailing garbage "2024-06-19 at the earliest"

📋 Generating an HTML Validation Report

write_validation_report() renders a self-contained HTML file — no external assets, opens straight from disk — summarizing validation results: a pass/fail overview per dataset/target, and a sortable, filterable table of every validation message with click-to-inspect detail. Clicking a message shows what the constraint actually requires (the allowed values for an enum violation, the declared type for an import error, a plain-language description of a failed rule) and the offending value — for group_condition rules, a full breakdown of the group, its conditions and constraints, and the affected rows.

R
write_validation_report(dta, file = "validation_report.html")

# Repeated identical messages are capped at max_repeats (default 5) with a
# "show all" toggle in the file itself -- raise or disable the cap:
write_validation_report(dta, file = "validation_report.html", max_repeats = Inf)
💡
Also in the Shiny app:

The same report is one click away from run_dta_app() — a "Report" download button sits next to the CSV/TSV/XLSX exports in the validation-messages dock.

🧩 group_condition Rule (Advanced)

group_condition applies if/then logic at the group level rather than row-by-row. First, rows are grouped (e.g., by SUBJECT_ID); then named conditions are evaluated across each group; finally, constraints specify which combinations of conditions must hold across the group.

YAML
- id: group_condition_example
  type: group_condition
  group_by:
    - SUBJECT_ID
  conditions:
    c_consent_yes:
      CONSENT:
        equals: "YES"
    c_consent_date_present:
      CONSENT_DATE:
        empty: false
  constraints:
    - id: consent_needs_date_per_subject
      type: requires
      if: c_consent_yes
      then: c_consent_date_present
      if_scope: any        # IF any row in the group matches
      then_scope: all      # THEN all rows in the group must match
💡
Reading the example above:

Group rows by SUBJECT_ID. For each subject group: if any row has CONSENT="YES", then all rows must have a CONSENT_DATE present.

🌊 Validating a File Too Large to Load

Everything so far reads the data into memory before checking it. For a file larger than the memory available that is not merely slow — it is impossible, because the table has to exist as an R object before a single row can be validated.

The answer is to scan the file in batches, holding one batch at a time. The ordinary way to ask for that is the stream argument on load_file(), which decides how the table is held once loaded.

R
# Read it into memory as an Arrow Table — the usual case.
dta <- load_file(dta, 1, file = "transfer.csv", stream = "never")

# Keep it lazy as an Arrow Dataset; check() scans it in batches.
dta <- load_file(dta, 1, file = "transfer.csv", stream = "always")

# Default "auto": "never" below 512 MB on disk, "always" above it.
dta <- load_file(dta, 1, file = "transfer.csv")

dta <- check(dta, quiet = TRUE)   # same verdict either way

TRUE and FALSE work as aliases for "always" and "never". Set the default and the threshold once per session:

R
options(DTAtools.stream = "always")              # or "never" / "auto"
options(DTAtools.stream_threshold = 2 * 1024^3)  # bytes; default 512 MB

# Tune the scan itself. Neither changes the counts or the verdict.
dta <- check(dta, batch_rows = 262144L, max_errors = 1000L)

Which one should you use?

SituationUseWhy
The file fits in memory comfortably "never" (or just the default) Roughly twice as fast, and import errors are reported immediately at load.
The file is larger than memory, or close to it "always" The only option that works at all. Memory stays flat regardless of row count.
You will validate the same table many times "never" Every scan re-parses the file from disk; an in-memory table is parsed once.
A large compressed file (.csv.gz) "always", explicitly "auto" compares the size on disk, which is far smaller than the materialised size — so it under-triggers here.
You just want a verdict, with no DTA object validate_file_stream() Same scan, same result shape, without building the object model.
You do not know, and sizes vary "auto" (the default) Small files stay fast; a file that would not fit switches by itself.
⚠️
Streaming finds import errors later, not fewer.

Both paths reach the same verdict and the same error counts. They differ in when: reading into memory coerces the columns during load_file() and records the issues there and then, while a lazy table has no rows yet — so its issues surface during check(). After a streaming load the dataset's @import_issues is empty until the check has run.

Without a DTA object at all, validate_file_stream() runs the same scan from specs and a path, returning the details list directly:

R
details <- validate_file_stream(specs, "transfer.csv")

details$ok                # TRUE / FALSE, the same three-axis verdict
details$n_columnspec_errors   # per-axis counts, as check() reports them
as.data.frame(details)    # one row per error: source, row, column, keyword, message

# Stop at the first problem rather than scanning to the end.
validate_file_stream(specs, "transfer.csv", fail_fast = TRUE)

# A missing column is decidable from the header alone.
validate_file_stream(specs, "transfer.csv", on_missing_column = "stop")

Nothing in the scan grows with the number of rows:

WhatBounded by
Column-spec checksthe batch size
Range and if/then rulesthe batch size
col_uniquethe number of distinct keys
group_conditionthe number of distinct groups
Retained error detailmax_errors
💡
This buys feasibility, not speed.

Measured across a sixteen-fold increase in input, the working set held by the scan stayed flat at about 19 MB while the in-memory path's grew from 51 MB to 272 MB — but scanning runs roughly twice as slow, because every batch pays its own overhead. Use it when holding the file is the problem; for a file that fits comfortably, check() is faster.

⚠️
A stopped scan is explicitly incomplete.

With fail_fast = TRUE the result carries a partial_scan attribute, lists only the rules that actually failed, and reports NA — not TRUE — for any axis it could not settle. A rule that has not failed yet has not passed: a duplicate further into the file was simply never read.

cache_as_parquet() rewrites a delimited file as Parquet so repeated validations skip re-parsing text. Measure before adopting it: on a file whose specs read every column it was not faster, because evaluating the constraints dominates and parsing is not the bottleneck.

📄 YAML Minimal Template

Copy-paste this as your starting point for any new spec:

YAML — copy-paste template
# Minimal DTAtools specification
