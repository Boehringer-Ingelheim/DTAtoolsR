- Why: `peak_during()` does `force(expr)` (:190), and `expr` is a promise bound to the calling frame, i.e. the per-size anonymous function inside `lapply` (:201). So the `tbl <- ...` (:212) and `typed <- ...` (:219) inside the `{ }` are assignments into that frame, exactly as `system.time({ x <- 1 })` leaves `x` behind. Nothing removes them before the streamed run (:223-225) or the after-gc RSS reads (:231-233): `tbl` (whole file as an Arrow Table, C++ pool) is only re-assigned at :239 and `rm(tbl, one_batch)` at :249 comes later; `typed` (a full typed data.frame in the R heap) is never removed at all. `peak_during`'s opening `gc(reset = TRUE, full = TRUE)` (:188) cannot free reachable objects and resets "max used" to the CURRENT use, which therefore already contains `typed`; the reported `stream_peak_mb` (:260) is the absolute figure, i.e. leftover + the scan's own peak, and `stream_rss_mb` / `stream_rss_after_gc_mb` (:192, :233) are read while both objects are alive. Committed CSV (its header equals the script's `out` columns): stream_rss_after_gc_mb 354.3 -> 495.6 -> 692.6 and stream_peak_mb 253.5 -> 351.8 -> 535.8 for 50k -> 200k -> 800k rows, against eager_hold_mb 49.8 -> 134.3 -> 312.2 and a flat stream_hold_mb 18.4 / 18.6 / 19.3. The growth of stream_peak_mb (+98, +184 MB) tracks that of eager_hold_mb (+85, +178 MB) to within ~16%, and at 50k rows stream RSS (354.3) already equals eager RSS (349.5) - consistent with the leftover dominating (inferred from sizes, not measured, as the finding itself says; eager_hold_mb is the size of a second, untyped re-read, so only an approximation of `typed`). Consequence: the script's reading of non-returning after-gc RSS as "the signature of symbol-table interning - a permanent leak" (:304-309) cannot work, and stream_hold_mb / eager_hold_mb are `object.size` figures of one batch / the whole frame (:239-248) - analytic, not measurements of the scan - so no measured column of the streamed run is uncontaminated and the claim at :5-12 is neither confirmed nor refuted. The suggested fix is sound and has precedent: bench_block_size.R re-invokes itself per configuration in a fresh `Rscript` child (`--one`, :160-221, :256-289). `rm(tbl, typed); gc()` alone would fix the R-heap column but probably not RSS (the script itself notes allocator high-water marks at :313-314; my inference), so a separate process is the cleaner fix.
