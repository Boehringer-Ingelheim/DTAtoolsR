Introduction

DTAtools automates the validation of tabular data against Data Transmission Agreement (DTA) and Data Transmission Specification (DTS) definitions. In regulated industries — clinical research, biomarker science, genomics — data must conform precisely to agreed column types, allowed values, and cross-column logic before it is transmitted between parties. Catching these errors programmatically, before submission, saves costly re-submissions and ensures reproducible, auditable data exchange.

DTAtools stores specifications in human-readable YAML files and provides an R API to:

  1. Import column specifications and semantic rules from YAML (or Word documents).
  2. Validate tabular data against those specifications — types, nullability, allowed values, regex patterns, and cross-column rules.
  3. Inspect validation results programmatically: which tables failed, which rows, which columns, which rules — and drill into individual errors with inspect().
  4. Export validated data to files (TSV/CSV, optionally gzip-compressed, with MD5 checksums).
  5. Generate Word documentation tables directly from specs — for use inside DTA/DTS documents.

DTAtools is built on the S7 object system and uses JSON Schema for fast, row-level validation.

Package Architecture

DTAtools organises objects into a layered hierarchy that maps directly to how a Data Transmission Specification (DTS) is structured:

The same hierarchy, as plain text:

DTA                              ← top-level agreement container
├── metadata                     ← title, version, receiver/supplier
|   (DTAMetaData)                     contacts, transmission schedule, ..
│                                     
└── datasets (named list of DTADataSet)  ← one or more datasets per DTS
    │
    ├── DTADataSetTabular        ← tabular data: for tables with
    |   |                            full column-spec + rule validation
    │   ├── files (list)         ← expected file handlers for various  
    |   |   |                        input types, manage file names, 
    │   │   ├── DTAFileCSV           which can have patterns, 
    |   |   ├── DTAFileTSV           number of files, etc ..
    |   |   └── DTAFileDelim
    │   │       └── read_file()  → Arrow Table
    |   |
    │   ├── specs (DTAColumnSpecCollection)  ← column-level schema +
    |   |   |                                   cross-column rules
    │   │   |
    │   │   ├── columns (named list of DTAColumnSpec)
    |   |   |   └── DTAColumnSpec × N   ← one per column: type, nullable,
    │   │   │                            values/pattern, length, format
    |   |   └── rules (list of DTARule)
    │   │       ├── DTARuleColCondition × N  ← if/then cross-column logic
    │   │       ├── DTARuleColRange × N      ← numeric range constraint
    │   │       └── DTARuleColUnique × N     ← uniqueness (single or 
    |   |                                              composite key)
    |   |
    │   └── tables (named list)  ← actual data as Arrow Tables
    │       └── <table_name>     ← populated via load_file() or constructor
    │
    └── DTADataSetFile           ← non-tabular: file presence/readability check
        ├── file_paths           ← character vector of expected file paths
        └── files (list)         ← DTAFile descriptors (derived from file_paths)

Three ways to build any object, from most to least common:

  1. read_dta_from_yaml() — a full DTA/DTS (metadata + one or more datasets). The recommended entry point for production use — see the Quickstart below.
  2. read_dataset_from_yaml() — a single, self-contained dataset definition (name, type, files, columns, rules — no top-level metadata:). Ideal when you only need to validate one dataset, e.g. while iterating on a spec.
  3. import_specs_from_yaml() — a bare list of column specs (just columns: plus optional rules:, no name/type/files). The most manual option: you build the DTADataSetTabular wrapper yourself.
  4. Programmatically in R — construct each class directly (e.g. DTAColumnSpec(), DTADataSetTabular())

Validation flow:

  1. load_file(dta, dataset, file) — reads a file into the dataset using its file handler
  2. check(dta) or check(ds) — runs JSON Schema validation + rule checks; returns the updated object
  3. results(x) — one-row-per-table summary (pass/fail, error counts)
  4. messages(x) — one-row-per-error detail table (column, row, rule, message, id)
  5. inspect(x, id = N) — deep-dive into a specific error message by its id

Quickstart

The canonical production workflow with a full DTA YAML: load the specification, load the data file, validate, inspect.

# 1. Load the full DTA definition from YAML
#    (metadata + dataset specs + file handlers + rules — all in one file)
dta <- read_dta_from_yaml(
  system.file("extdata", "clinical_dta.yaml", package = "DTAtools")
)
print(dta)

csv_path <- system.file("extdata", "clinical_data.csv", package = "DTAtools")

Quickstart Variant: A Single Dataset with read_dataset_from_yaml()

Not every delivery needs a full DTA with metadata. When you only need to validate one dataset — while iterating on a spec, or when metadata is tracked elsewhere — read the dataset definition directly with read_dataset_from_yaml(). This is the second most common entry point into DTAtools, right after read_dta_from_yaml().

A standalone dataset YAML has exactly the same shape as one entry under a DTA’s datasets: list — name, type, files, columns, rules — just without the surrounding metadata:/datasets: wrapper. The package ships a real example of this shape at inst/extdata/gf_dataset.yaml; here we build an equivalent one by extracting the clinical_data entry from clinical_dta.yaml so the example stays self-contained:

# Extract one dataset entry so it stands alone (same shape as gf_dataset.yaml)
full_yaml    <- yaml::read_yaml(
  system.file("extdata", "clinical_dta.yaml", package = "DTAtools")
)
dataset_yaml <- tempfile(fileext = ".yaml")
yaml::write_yaml(full_yaml$datasets[[1]], dataset_yaml)

# 1. Load the single-dataset definition — no metadata needed
ds <- read_dataset_from_yaml(dataset_yaml)
ds     # a ready-to-use DTADataSetTabular, specs + file handler already set
#> <DTADataSetTabular> : clinical_data
#> ℹ Files: 1 entry with a total of 1 file
#> → clinical_data.*.csv$ (1)
#> ℹ Specs:
#> → columns (14): STUDYID, VISIT, AGE, GENDER, INCLUDE, HEIGHT, WEIGHT, ..., SUBJECT_ID
#> → rules (6): rule_equal_example, rule_unequal_example, rule_range_example, rule_dependency_example, ..., check_col_condition_example

# 2. Load the data file — same load_file() call as for a full DTA, just

Column Specifications

The DTAColumnSpec Object

A DTAColumnSpec represents a single column’s metadata and constraints. It maps directly to a column entry in a YAML specification.

Field Required Description
id ✔ Column name (must match the data frame header exactly)
label Human-readable label for documentation
type SAS-style type: SAS Char, SAS Num, SAS Int
format SAS format string, e.g. SAS $10., SAS 8.
length Maximum character length (maxLength in JSON Schema)
nullable TRUE/FALSE — whether the column may be empty/NA
values Closed list of allowed values (enum in JSON Schema)
pattern Regular expression every value must match
description Free-text description for documentation

Note: values and pattern are mutually exclusive — a column either has a closed value list or a regex pattern, not both.

# A column with a closed value list
visit_col <- DTAColumnSpec(
  id          = "VISIT",
  label       = "Visit Code",
  type        = "SAS Char",
  length      = 12,
  nullable    = FALSE,
  values      = list("V01", "V02", "V03", "EOT"),
  description = "Planned study visit code"
)
print(visit_col)

The DTAColumnSpecCollection Object

A DTAColumnSpecCollection groups column specs together, optionally with a set of schema rules. This is the core specs object passed to DTADataSetTabular.

# Build a collection manually
studyid_col <- DTAColumnSpec(
  id = "STUDYID", type = "SAS Char", nullable = FALSE,
  values = list("1234-5678")
)
gender_col <- DTAColumnSpec(
  id = "GENDER", type = "SAS Char", nullable = FALSE,
  values = list("Male", "Female", "Other")
)

specs <- DTAColumnSpecCollection(
  columns = list(
    STUDYID = studyid_col,
    VISIT   = visit_col,
    AGE     = age_col,
    GENDER  = gender_col,
    AE_TERM = ae_col
  )
)
print(specs)
#> <DTAColumnSpecCollection>
#> ℹ columns (5): STUDYID, VISIT, AGE, GENDER, AE_TERM
#> → rules: ✖

# Access individual column specs
names(specs)

colspec(specs, "VISIT")

Use Case 3: Bare Specs with import_specs_from_yaml()

read_dta_from_yaml() and read_dataset_from_yaml() (both shown in the Quickstart above) cover the vast majority of use cases. The third, most manual option is import_specs_from_yaml(): it reads only the columns key (plus an optional rules key) from a YAML file — ignoring any name, type, or files keys — and returns a bare DTAColumnSpecCollection with no dataset wrapper. Use it when you already manage the data table and dataset naming yourself and just need the column/rule definitions, e.g. to build a DTADataSetTabular by hand as shown further below.

# The package ships with a real standalone dataset YAML — import_specs_from_yaml()
# reads only its `columns`/`rules` keys, ignoring name/type/files
yaml_file <- system.file("extdata", "gf_dataset.yaml", package = "DTAtools")
gf_specs <- import_specs_from_yaml(yaml_file)
print(gf_specs)
#> <DTAColumnSpecCollection>
#> ℹ columns (33): STUDYID, DOMAIN, SUBJIDN, GFGRPID, GFREFID, GFTESTCD, GFTEST, ..., SWVER
#> ℹ rules (7): check_equals, unequal_check, unique_check, GFORRES_must_have_a_range, ..., overlap_check

Creating a DTADataSetTabular

A DTADataSetTabular combines a DTAColumnSpecCollection with one or more data tables. Tables are stored internally as Arrow Tables for performance.

# Load the clinical DTA specs from a full DTA YAML (metadata + datasets)
clinical_yaml <- system.file("extdata", "clinical_dta.yaml", package = "DTAtools")
dta_obj       <- read_dta_from_yaml(clinical_yaml)

# The DTA contains one dataset called "clinical_data" — but tables are empty
# until you load data into them
datasets(dta_obj)
#> $clinical_data
#> <DTADataSetTabular> : clinical_data
#> ℹ Files: 1 entry with a total of 1 file
#> → clinical_data.*.csv$ (1)
#> ℹ Specs:
#> → columns (14): STUDYID, VISIT, AGE, GENDER, INCLUDE, HEIGHT, WEIGHT, ..., SUBJECT_ID
#> → rules (6): rule_equal_example, rule_unequal_example, rule_range_example, rule_dependency_example, ..., check_col_condition_example
#> ℹ Tables: none
ds_spec <- datasets(dta_obj, "clinical_data")
ds_spec   # specs defined, no tables yet
#> <DTADataSetTabular> : clinical_data
#> ℹ Files: 1 entry with a total of 1 file
#> → clinical_data.*.csv$ (1)
#> ℹ Specs:
#> → columns (14): STUDYID, VISIT, AGE, GENDER, INCLUDE, HEIGHT, WEIGHT, ..., SUBJECT_ID
#> → rules (6): rule_equal_example, rule_unequal_example, rule_range_example, rule_dependency_example, ..., check_col_condition_example
#> ℹ Tables: none

The most flexible approach is to combine specs with your own data:

# Get specs from the full DTA spec
clinical_specs <- specs(ds_spec)

# Read the CSV independently
csv_path   <- system.file("extdata", "clinical_data.csv", package = "DTAtools")
raw_data   <- read.csv(csv_path)

# Create the DTADataSetTabular with specs + data, then validate
ds <- DTADataSetTabular(
  name   = "clinical_data",
  specs  = clinical_specs,
  tables = list(clinical_data = raw_data)
)
ds
#> <DTADataSetTabular> : clinical_data
#> ℹ Files: none
#> ℹ Specs:

# Build specs
col_studyid <- DTAColumnSpec(id = "STUDYID", type = "SAS Char", nullable = FALSE,
                             values = list("STUDY001"))
col_visit   <- DTAColumnSpec(id = "VISIT",   type = "SAS Char", nullable = FALSE,
                             values = list("SCREENING", "BASELINE", "WEEK4"))

inline_specs <- DTAColumnSpecCollection(
  columns = list(STUDYID = col_studyid, VISIT = col_visit, AGE = col_age)
)

# Build data
inline_data <- data.frame(

# Combine into a DTADataSetTabular

Validating with check()

check() runs two validation passes:

  1. JSON Schema validation — checks every row against column types, nullable, values, pattern, and length.
  2. Schema rule validation — evaluates inter-column rules (col_condition, col_range, col_unique).

check() always returns the updated object — assign the result back.

Validating a dataset

ds <- check(ds)
#> 
#> ── Table 1 of 1: clinical_data ─────────────────────────────────────────────────

Inspecting Validation Results

Drilling into Errors with inspect()

messages() gives you a row per error with an id column. When you want the full story behind a specific error — the exact cell value, the row in context, the JSON Schema constraint that failed, or the rows that violated a rule — call inspect(x, id = N).

messages(x)    → per-error table — note the `id` of the error you care about

Schema Rules

Schema rules are defined alongside column specs and express inter-column constraints that cannot be captured by JSON Schema alone.

Rule Types

col_condition — If/Then Logic

The most versatile rule type. When condition is satisfied for a row, the then block is enforced on that same row.

Supported operators in both condition and then:

Operator Applies to Example
equals string / number equals: "YES"
not_equals string / number not_equals: "DROPPED"
empty any (true/false) empty: true
in list in: [V01, V02, EOT]
not_in list not_in: [REJECTED]
pattern string regex pattern: "^SUBJ[0-9]{4}$"
greater number greater: 0
greater_equal number greater_equal: 18
less number less: 200
less_equal number less_equal: 65
min / max number range min: 10 + max: 100 
rules:
  # IF consent was given, consent date must be filled in
  - id: consent_requires_date
    type: col_condition
    condition:
      CONSENT:
        equals: "YES"
    then:
      CONSENT_DATE:
        empty: false

  # IF visit is V03, status must be COMPLETED
  - id: v03_must_be_completed
    type: col_condition
    condition:
      VISIT:
        equals: V03
    then:
      STATUS:
        equals: COMPLETED

  # IF sample has no reason for test not done, result must be present
  - id: result_when_no_reason
    type: col_condition
    condition:
      GFREASND:
        empty: true
    then:
      GFORRES:
        empty: false

  # Multiple conditions and multiple then-clauses are fully supported
  - id: v03_full_check
    type: col_condition
    condition:
      VISIT:
        equals: V03
    then:
      STATUS:
        equals: COMPLETED
      AGE:
        min: 18
        max: 65
      WEIGHT:
        greater_equal: 5

col_range — Numeric Range Check

Enforces that all values in a numeric column fall within [min, max].

rules:
  - id: age_range
    type: col_range
    column: AGE
    min: 18
    max: 65

col_unique — Uniqueness Constraint

Enforces that all combinations of values across one or more columns are unique. Specifying multiple columns checks the combined key for uniqueness.

rules:
  # Single column uniqueness
  - id: subject_unique
    type: col_unique
    column: SUBJECT_ID

  # Composite key uniqueness: SUBJECT_ID + VISIT must be unique per row
  - id: subject_visit_unique
    type: col_unique
    column:
      - SUBJECT_ID
      - VISIT

Defining Rules in R

Rules can also be constructed programmatically:

# col_range rule
range_rule <- DTARuleColRange(id = "age_range", columns = "AGE", min = 18, max = 65)

# col_condition rule: IF CONSENT == "YES" THEN CONSENT_DATE must not be empty
condition_rule <- DTARuleColCondition(
  id        = "consent_requires_date",
  condition = list(CONSENT = list(equals = "YES")),
  then      = list(CONSENT_DATE = list(empty = FALSE))
)

DTADataSetFile: File Presence and Readability Checks

While DTADataSetTabular validates the content of a delivered file against a column schema and rules, DTADataSetFile answers a more basic question: did the expected files actually arrive, and can we open them?

Use DTADataSetFile when a DTS requires that certain non-tabular files (PDFs, archives, reports, audit logs, raw instrument output) are present and non-empty — without caring about their internal structure.

check() for a DTADataSetFile verifies each path:

Exporting Data and Documentation

Write Validated Tables to File

write_table_to_file() writes a named table from a DTADataSetTabular to disk. It optionally computes and writes an MD5 checksum sidecar file.

# Validate the clinical dataset
csv_path_w    <- system.file("extdata", "clinical_data.csv", package = "DTAtools")
dta_obj_w     <- read_dta_from_yaml(
  system.file("extdata", "clinical_dta.yaml", package = "DTAtools")
)
ds_w <- DTADataSetTabular(
  name   = "clinical_data",
  specs  = specs(datasets(dta_obj_w, "clinical_data")),
  tables = list(clinical_data = read.csv(csv_path_w))
)
ds_w <- check(ds_w, quiet = TRUE)

# Write to TSV (tab-separated, sorted by SUBJECT_ID)
out_tsv <- tempfile(fileext = ".tsv")
write_table_to_file(
  DTADataSetTabular = ds_w,
  table             = "clinical_data",
  filename          = out_tsv,
  sep               = "\t",
  arrange_by        = "SUBJECT_ID",
  get_md5sum        = FALSE
)
#> ℹ Arrange table by SUBJECT_ID.
#> ℹ Write table to C:\Users\schwarz8\AppData\Local\Temp\RtmpqU8Aje\filea36499d19a5.tsv.

Key arguments for write_table_to_file():

Argument Default Description
sep "\t" Field separator ("," for CSV, "\t" for TSV)
arrange_by "all" A single column name to sort by, "all" to sort by all columns, or NULL to skip sorting
compression "none" "none" or "gzip"
get_md5sum TRUE Compute and print the MD5 checksum of the written file
write_md5sum_to_file TRUE Write MD5 + row/column count to a .md5 sidecar file
overwrite TRUE Whether to overwrite an existing file

YAML Format Reference

Column Specification

columns:
  # Minimal example — id + type + nullable
  - id: STUDYID
    label: Study Identifier
    type: SAS Char
    nullable: false
    length: 10
    values:
      - 1234-5678
    description: Unique identifier for the study

  # Closed value list
  - id: GENDER
    label: Gender
    type: SAS Char
    nullable: false
    values:
      - Male
      - Female
      - Other

  # Regex pattern (mutually exclusive with values)
  - id: SUBJECT_ID
    label: Subject Identifier
    type: SAS Char
    nullable: false
    pattern: "^SUBJ[0-9]{4}$"

  # Numeric column, nullable
  - id: AGE
    label: Age (years)
    type: SAS Num
    nullable: false
    description: Age in whole years at baseline

  # Nullable character (empty/NA is allowed)
  - id: AE_TERM
    label: Adverse Event Term
    type: SAS Char
    nullable: true
    description: Adverse event verbatim term, empty if no event

Supported types: SAS Char, SAS Num, SAS Int

Nullable values: true/false or Yes/No

Schema Rules

rules:
  # ── col_condition ──────────────────────────────────────────────────────────
  # IF CONSENT == "YES" THEN CONSENT_DATE must not be empty
  - id: consent_requires_date
    type: col_condition
    condition:
      CONSENT:
        equals: "YES"
    then:
      CONSENT_DATE:
        empty: false

  # IF VISIT == V03 THEN STATUS must be COMPLETED
  - id: v03_completed
    type: col_condition
    condition:
      VISIT:
        equals: V03
    then:
      STATUS:
        equals: COMPLETED

  # IF GFREASND is populated THEN GFORRES must be empty (mutual exclusivity)
  - id: mutual_exclusivity
    type: col_condition
    condition:
      GFREASND:
        empty: false
    then:
      GFORRES:
        empty: true

  # Multiple then-clauses: age range, weight lower bound, status check
  - id: v03_full_checks
    type: col_condition
    condition:
      VISIT:
        equals: V03
    then:
      STATUS:
        equals: COMPLETED
      AGE:
        min: 18
        max: 65
      WEIGHT:
        greater_equal: 5

  # Pattern matching in condition
  - id: internal_supplier
    type: col_condition
    condition:
      GFREFID:
        pattern: "^Internal_[0-9]+$"
    then:
      GFNAM:
        equals: "Internal"

  # ── col_range ──────────────────────────────────────────────────────────────
  # AGE must be between 18 and 65 (inclusive)
  - id: age_range
    type: col_range
    column: AGE
    min: 18
    max: 65

  # ── col_unique ─────────────────────────────────────────────────────────────
  # SUBJECT_ID must be globally unique
  - id: subject_unique
    type: col_unique
    column: SUBJECT_ID

  # The combination of SUBJECT_ID + VISIT must be unique
  - id: subject_visit_unique
    type: col_unique
    column:
      - SUBJECT_ID
      - VISIT
